# 图片 Source 实验可行性与能力验证

这项实验值得继续，最适合保存报错截图、界面状态和简单架构图中的工作证据。推荐链路是「拿到原始图片 → 耐久保存 → 后台解析 → 保存有来源的文字解读 → 既有记忆流程」。原图用于核查，解析用于检索；识图成功并不等于已经生成了可靠记忆。

公开资料、现有代码、真实 Codex CLI 受控附件探测和服务联调已完成。MiniCPM-V-4.7-35B-A3B 已完成真实识图；CLI 0.141.0、0.162.0-alpha.2 与 0.162.0-alpha.17.2 exec 已接入，Desktop 同款运行内核已通过独立采集器与真实 Vision 联调，用户三次实际桌面单 PNG 发送也已回读验证。真实 DeepSeek 已自动从图片解析生成 Memory，BGE-M3 向量、关键词和混合检索及原始材料回图已验证。拖图／粘贴差异、多附件与全新桌面聊天的实际召回仍待验收，1B 与交互 TUI 未开放。最新证据见 [Codex 附件证据](codex-capture-evidence.md)。

## 价值和适用边界

| 图片内容 | 可能获得的价值 | 需要保留的限制 |
| --- | --- | --- |
| 报错截图、日志截图 | 找回错误文字、版本与当时界面，减少重复描述 | 截图中的报错不能直接证明根因；小字必须能够回图核查 |
| 配置页、UI 状态 | 保存文字会话没有记录的设置和状态 | 单张图只反映该时刻，不能自动认定为长期配置或用户偏好 |
| 简单架构图、草图 | 保存可见组件和连线，帮助后续会话理解背景 | 箭头方向、复杂关系容易误读；草图不能变成已确认决策 |
| 已有完整文字记录的截图 | 保留原始凭据，检索收益可能较小 | 应比较开启与关闭时的实际召回收益，避免重复独立计权 |
| 大量照片、无关图、密集表格 | 本实验收益不明确 | 首版不扩展成图片素材库、表格解析器或通用多模态产品 |

价值主要来自跨会话复用和来源核查，而不只是一次 OCR。实际收益、错误率、延迟和成本要在阶段七用配对任务测量。当前有 35B 单样本验证，没有两个候选模型的对比数据，不能依据参数规模选定默认模型。

## 已核实的技术基础

现有 Source 系统具备类型定义、不可变身份、Scope 分区、journal 和 `powercontext.text-evidence` 投影。图片原始字节应单独存储，两个新的原生 Source 保存资产和解析信息；不需要全局改造 SourceRef，也不需要先建设图片向量检索。具体接入点见 [现有系统接入分析](contract-integration-analysis.md)。

当前通用结构化生成器将输入序列化成文字 JSON，不能通过添加图片路径或 Base64 字符串获得真正的视觉输入。Pydantic AI 支持 `BinaryContent` 等多模态输入，但具体模型支持仍由 provider 决定。后续应复用模型连接和用量机制，单独增加图片输入适配。[Pydantic AI 多模态输入](https://pydantic.dev/docs/ai/core-concepts/input/)

MCP 的 `tools/call` 传入工具参数，不会自动把宿主上传的图片广播给连接的 Server。自动接入需要宿主提供附件，或者经验证的宿主适配器主动提交图片字节。[MCP 工具协议](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

### 两个会影响实现的实测发现

**提交前 hook 不是可靠的图片接收时机。** CLI 样本的 `UserPromptSubmit` 只有文字和轮次字段。当时 transcript 已存在，但当前轮次的用户图片尚未写入。普通 Stop 时记录才可用于定位本轮附件。官方也明确 transcript 格式不是稳定的 Hook 接口。[Codex Hook 输入](https://learn.chatgpt.com/docs/hooks#userpromptsubmit)

**transcript 图片不一定是上传原图。** 自制 3000×2000 PNG 的原文件为 22,208 字节，模型输入图为 2048×1365、57,622 字节，两者摘要不同。小 PNG 和 JPEG 相同只证明对应样本。旧 CLI 读取经过验证的原文件；Desktop 和现代 CLI 保留宿主实际提交的图片表示并明确标为 host_image，不能把缩放后的输入声称为磁盘原图。

rollout 中的用户消息没有自己的 `turn_id`，必须使用前面的 `turn_context.turn_id` 建立轮次边界，再关联 `local_images` 和附件位置。不能查找“最后一张图”，也不能通过相同文字认定同一附件。app-server 自建客户端有明确的 `turn.id`，这不意味着外部插件可以连接 Desktop 的既有进程。[Codex app-server 类型生成](https://learn.chatgpt.com/docs/app-server#message-schema)

自动路线已实现：显式授权与 Scope 绑定后，CLI Hook 注册当前轮次，Desktop collector 只查询授权项目的索引，两端增量取得明确消息并暂存，使用同一耐久投递队列。未知格式或无法关联的记录拒绝，已有聊天从启用时 EOF 开始，不补导历史或关闭期间的图片。旧 CLI 保留原文件校验，现代宿主明确保存 host_image。实际预算和恢复规则见固定契约。

## 模型接口与候选能力

公开 OpenBMB API 文档展示 OpenAI Chat 风格接口：`/v1/chat/completions`、Bearer 凭据，以及文字与 `image_url` 内容块。它支持以 data URI 携带图片。公开示例可以指导适配器设计，但没有证明本用户两个内测型号的精确 ID、endpoint 或兼容能力。[OpenBMB API 指南](https://github.com/OpenBMB/MiniCPM-V/blob/main/docs/api.md)

| 检查项 | MiniCPM-V-4.7-1B | MiniCPM-V-4.7-35B-A3B | 首版处理 |
| --- | --- | --- | --- |
| 用户具有内测访问条件 | 用户已说明 | 用户已说明 | 接受该前提，不调查账号或索取聊天中的密钥 |
| 精确服务 model ID、endpoint、部署版本 | 待提供本地配置 | 已配置精确 35B ID 与面壁 endpoint；部署标识为本地标签 | 不用公开型号替代，不猜测服务名称 |
| Chat 多模态图片输入 | 待真实验证 | 真实单图请求与 worker 已通过 | 选作候选协议，实际返回决定是否适配 |
| 中文 OCR、小字、关系、模糊图 | 待真实验证 | 中文 OCR 样本通过；小字、关系和模糊图质量未验收 | 使用同一测试集比较，保留不确定项 |
| 提示要求 JSON 与本地 schema 校验 | 待真实验证 | 严格六字段 JSON 已通过，非法换行明确失败 | 首版选择提示 JSON；无效输出明确失败 |
| 原生 JSON Schema、工具调用、Responses、detail | 未验证 | 未验证 | 首版不依赖这些能力 |
| 超时、429／5xx、usage 与延迟 | 待真实验证 | 真实 usage 与耗时已记录；错误与重试使用受控 HTTP 验证 | 未知用量不填零，有限尝试计入统一预算 |
| 本机端侧部署、显存和权重获取 | 未验证 | 未验证 | 调用已部署 endpoint，核心包不管理推理环境 |

“OpenAI compatible”不保证全部参数或输出功能兼容。部署框架也可能只支持一部分字段，例如 vLLM 对部分图像参数有不同支持范围。首版先用最小的文字加单图请求，不发送未验证的 `detail`、Files 或 Responses 专用参数。[vLLM 兼容服务说明](https://docs.vllm.ai/en/latest/serving/online_serving/openai_compatible_server/)

Pydantic AI 的结构化输出方式应明确选为提示 JSON，并限制单次模型请求；不能默认依赖工具调用，再叠加框架修复请求和 worker 重试。模型输出只包含可见内容和不确定项，来源和成功状态由服务填写。

## 保留待补项的复现方法

真实模型验证在 `.powercontext/image-source-experiment/` 内使用独立配置、日志和脱敏样本。API key 保留在本地受保护配置中，文档只登记配置路径、无密钥的 endpoint、实际 model ID、部署版本和响应摘要。35B 连接与真实请求结果见 [解析与记忆说明](phase34-usage.md)，证据保存在忽略目录 phase34；公开内容不含 Key。

| 样本／检查 | 应记录的结果 | 合格含义 |
| --- | --- | --- |
| 自制色块图，图中文字未出现在提示中；红蓝分别请求 | 实际颜色、隐藏文字及输出 | 模型确实使用图片，不能只回答提示中的文字 |
| 自制中文配置页、报错页、带方向的简图 | OCR、可见关系和不确定项 | 结果可回图验证，不能编造根因或决策 |
| 模糊小字、空白图、图片-only 上下文 | readability、空结果和不确定项 | 能承认不可读，不强制生成事实 |
| PNG、JPEG、透明度和 EXIF 方向 | 实际请求格式、预处理摘要、图片方向 | 原图保持不变，模型输入预处理可追溯 |
| 严格输出 schema、额外字段、缺少字段 | 本地校验结果 | 未通过不能写有效解析 Source |
| 超时、断连、429／5xx、无效 JSON | 状态、尝试数、延迟、usage | 先模拟可控失败，再记录真实服务实际出现的响应；不能故意打满服务 |
| endpoint 返回模型别名、未返回 usage | 配置 ID、服务实际返回字段 | 不编造权重版本或 token 数；无法固定部署版本列为限制 |

每个真实候选至少覆盖以上内容，再决定是否启用该配置。性能和费用比较留到阶段七，不要求阶段零把几十张工作图发给服务。模型支持多图与否不是首版验收条件。

Desktop 待补界面验证应分别拖入、粘贴、只传图和传多图，记录回执、任务状态、消息身份和保存图片摘要。运行内核、实际 Hook、独立 collector、真实 Vision、真实普通模型 Memory 与后端召回已有证据，但不能替代这些实际界面操作及全新桌面聊天的自动注入验收。

## 可进入开发的结论

阶段二至六已接入显式上传、后台解析、文字消费、精确回溯、固定 CLI 捕获、可选配置引导和原图查看。35B 与实际 CLI 文件附件联调已通过，具体入口见 [捕获与查看说明](phase56-usage.md)。下一阶段用工作图片评估质量、费用、延迟与跨会话收益。

模型或自动宿主未验证，不阻止无凭据的本地实现；它们会限制后续的可用性承诺。任何安装引导都不能预选未经验证的内测 endpoint，也不能把“功能已打开”展示成“当前宿主已经自动接图”。

当前最重要的工程风险已有明确约束：原图与模型输入分开，原图过滤集中处理，配置快照固定，不同重试含义明确，资产和 SQLite 提交可恢复，同 Scope 权限贯穿回图路径。具体字段、预算与验收以 [阶段一契约](contracts.md) 为准。
